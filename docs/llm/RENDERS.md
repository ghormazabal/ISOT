# Renders: guía para agentes de IA (LLM)

Objetivo: escribir o modificar **templates de render** de ISoT a partir de
una descripción («quiero un Netplan por nodo con bonds y VLANs», «un YAML con
todas las NAD del clúster»…) y declarar sus **instancias**. El usuario lo
revisa y guarda desde la web (Renders → Plantillas); tú produces archivos.

Guía para personas: [docs/renders/GUIDE.md](../renders/GUIDE.md). Esquemas:
`schemas/render-context.schema.json` (contexto), `schemas/render-template.schema.json`
(`template.yaml`) y `schemas/renders.schema.json` (`renders.yaml`).

## 0. Límite (obligatorio)

- El repo de ISoT solo contiene el motor, templates genéricos
  (`templates/manifests/`, **solo lectura**) y ejemplos ficticios.
- Datos reales, templates de un cliente y **toda salida renderizada** van al
  repo de datos (`manifest-templates/`, `renders.yaml`, `rendered/`). Nunca
  escribas salidas ni templates de cliente dentro de ISoT.
- **Un solo repositorio**: un render funciona enteramente dentro del mismo
  repo de datos. El destino es solo una carpeta de ese repo; ISoT nunca mueve
  ni escribe nada de un repositorio a otro (no existen `targets`,
  `default_target` ni `target_repos`; si los ves en un `renders.yaml`, son un
  error).
- Para personalizar un template incluido, cópialo a
  `manifest-templates/<nuevo-id>/` del repo de datos con otro `id`.
- No inventes datos: si algo no está en el contexto, no existe. No pongas
  secretos en templates ni en params.

## 1. Archivos

```
<repo de datos>/
  renders.yaml                      # instancias y destinos
  sites/<sitio>/renders.yaml        # (opcional) instancias de un sitio
  manifest-templates/<id>/
    template.yaml                   # spec
    *.j2                            # Jinja2 (salidas y macros)
  rendered/…                        # salida (mismo repo), con .isot-render.json
```

## 2. `template.yaml`

| Clave | Tipo | Notas |
|---|---|---|
| `id` | str | `^[a-z0-9][a-z0-9._-]*$`, igual a la carpeta |
| `version` | int/str | Súbela cuando cambie la salida (el diff marca «versión vieja») |
| `description`, `tags` | str, [str] | Para la biblioteca |
| `scope` | `site` \| `cluster` \| `device` | `cluster` exige instancia con clúster; `device` = for_each por defecto `devices` |
| `for_each` | expr Jinja → lista | Elementos para `per_item` (y `items` en `single`) |
| `where` | expr Jinja → bool | Filtro por `item` |
| `params` | map | Defaults; los params de la instancia los sobrescriben clave a clave |
| `outputs` | lista | `template` (archivo .j2), `mode` (`single`/`per_item`), `path` (Jinja), opcional `for_each`, `where`, `header` (bool), `description` |

Reglas de `path`: relativo, sin `..`, sin `/` inicial, sin `.git`, segmentos
`[A-Za-z0-9._-]`; rutas únicas; `.isot-render.json` reservado. Límites: 2000
archivos, 256 KiB por fuente, 4 MiB por salida.

## 3. Motor

Jinja2 `SandboxedEnvironment` con `StrictUndefined` (una variable o clave
inexistente es un error con archivo:línea), `trim_blocks` y `lstrip_blocks`.
Los `.j2` del mismo template se pueden importar/incluir por nombre
(`{% import 'macros.j2' as m %}`). Se añade la cabecera
`# GENERATED BY ISoT — DO NOT EDIT` a `.yaml`, `.yml`, `.conf`, `.cfg`,
`.txt`, `.sh`, `.toml`, `.ini`, `.env`, `.properties` y archivos sin
extensión, seguida de `# template: <id>@<versión> · instance: <id>` (`header: false` la quita, `header: true` la fuerza, p. ej. en `.json` no se pone por defecto). El final de archivo
se normaliza a un único `\n`.

Filtros añadidos: `ip_address` (`10.0.0.5/24`→`10.0.0.5`), `prefixlen`,
`netmask`, `network`, `with_prefix(cidr)`, `to_yaml`, `to_json(indent)`,
`flatten`, `explode(attr)` (→ `[{parent, value}]`), `vlan_list`
(`"10,20-22"`→`[10,20,21,22]`), `regex_replace(pat, repl)`. Más los de Jinja
(`selectattr`, `map`, `unique`, `default`, `indent`…).

## 4. Contexto (`context_version: 1`)

| Variable | Contenido |
|---|---|
| `site` | `id, name, description, domain, dns_servers[], dns_search[], ntp_servers[], http_proxy, https_proxy, no_proxy, subnets[], vlans[]` |
| `subnets[]` | `name, cidr, vlan, gateway, purpose…` |
| `devices[]` | Equipos del sitio; **solo los miembros del clúster** si la instancia tiene `cluster` |
| `site_devices[]` | Todos los equipos del sitio |
| `cluster` | `None` o `name, site, kind, distro, version, template_ref, pod_cidr, service_cidr, cni, nads[], metallb{version, mode, pools[], services}, vips, nodes[], members[], namespaces[], helm_values, vms[], path, raw` |
| `clusters[]`, `vms[]` | Clústeres del sitio; VMs (del clúster si hay) |
| `params`, `instance`, `template` | Params efectivos; `{id, …}` de la instancia y del template |
| `item`, `index` | En `per_item` |
| `items` | En `single` si hay `for_each` |
| `subnet(name)`, `subnet_by_vlan(id)`, `device(hostname)` | Búsquedas (`None` si no existe) |

Equipo (`devices[]`): `hostname, name (minúsculas), site, role, kind
(baremetal, vm, switch…), k8s_roles[], cluster, os, vendor, model, labels,
bonds[{name, mode, mtu, members[], allowed_vlans[], extra_host_vlans[],
leaf_pc, note}], interfaces[{name, parent, vlan, ip, address, prefix,
gateway, network, subnet, subnet_cidr, nad, mtu, mac, connected_to}], oob,
primary_ip, hypervisor, resources, path, raw`.

NAD (`cluster.nads[]`): campos del inventario más `cidr` y `gateway` de su
subred. Pool MetalLB: `name, addresses[], auto_assign, subnet, l2_interfaces[]`.

Secretos: `password`, `token`, `secret`, `community`, `*_key`… llegan como
`<redacted>`; si una salida parece llevar un secreto el motor avisa
(`REN-002`).

**Trampa**: en Jinja `d.values`, `d.items`, `d.keys` son métodos del dict. No
uses claves con esos nombres; por eso los values de Helm son
`cluster.helm_values`. Usa `d['clave']` si dudas.

## 5. `renders.yaml`

```yaml
version: 1
target_dir: rendered          # carpeta destino por defecto, en este mismo repo
instances:
  - id: site1-netplan         # único
    template: netplan-node
    site: site1
    cluster: site1-apps       # opcional
    target_dir: gitops/clusters  # opcional; otra carpeta de este mismo repo
    dir: a/b                  # opcional; por defecto <sitio>/<clúster o "site">/<template>
    params: {default_mtu: 9000}
    enabled: true
    description: …
```

## 6. Diff y aplicar

ISoT renderiza en memoria y compara con `<target_dir>/<dir>` del mismo repo
de datos: `new`, `modified`, `unchanged`, `orphaned`. «Aplicar» (solo en
modo edición, con confirmación del diff) escribe los archivos y el
`.isot-render.json` en una rama `wizard/…` de ese mismo repo. Se rechazan
destinos con `..`, absolutos, por `.git`, enlaces simbólicos que escapan del
repo y cualquier ruta dentro de la instalación de ISoT. No intentes
saltarte estas comprobaciones.

**Preview vs guardar.** `POST /api/renders/preview` solo calcula (no escribe).
Para guardar la salida de una preview en su carpeta destino, la UI usa
`POST /api/renders/save/status` (solo lectura: destino, `state` =
`al_dia|desfasado|no_existe|error`, instancia o `new_instance` propuesta),
`/api/renders/save/preview` y `/api/renders/save/commit` (edición; cuerpo
`{template, site, cluster, instance, params, create_instance?,
new_instance_id?, prune?, message?, branch?}`), equivalentes a Aplicar para
una sola instancia. Sin instancia que coincida (template, sitio, clúster y
params) hay que crearla (`create_instance: true`), y entra en `renders.yaml`
en el mismo commit. Tú (LLM) no llamas a esta API: propone el template y la
instancia, y que la persona guarde desde la UI o con un commit propio
seguido de `isot index`.

Con **Comparar** (barra superior, `?base=&head=`), la pestaña Diff ofrece
destino en base vs render en head, salida base → head
(`GET /api/renders/compare?base=&head=`) y diff de `manifest-templates/` +
`renders.yaml`. Cualquier lado puede ser `local` (working tree).

**Índice (obligatorio)**: si añades o cambias archivos fuera de la UI
(`manifest-templates/`, `renders.yaml`, `rendered/`), ejecuta
`isot index --repo <repo>` y commitea los `_*_index.json` y
`_index_manifest.json` en el mismo commit. `isot index --check` debe pasar;
si no, la regla `IDX-001` avisa y la CI falla.

## 7. Procedimiento para escribir un template desde una descripción

1. Identifica el **alcance** (sitio, clúster, por equipo) y la **unidad de
   salida** (un archivo total → `single`; uno por nodo/interfaz → `per_item`
   con `for_each`/`where`, usando `explode` para pares nodo×interfaz).
2. Lista los campos del contexto que necesitas (§4). Si falta un dato en el
   inventario, no lo inventes: usa `params` con default o
   `| default(...)` y dilo en tu respuesta.
3. Pon la lógica común en una macro (`macros.j2`) si hay varias salidas del
   mismo contenido (per_item + single).
4. Escribe `template.yaml` (§2) y los `.j2`. Sin secretos.
5. Propón la instancia para `renders.yaml` (§5).
6. Pide al usuario que pegue los archivos en Renders → Plantillas (o que los
   commitee en `manifest-templates/<id>/`) y revise la preview, los errores
   (archivo:línea) y la pestaña Diff antes de aplicar. Si los commiteas tú,
   corre `isot index --repo <repo>` antes del commit.

## 8. Ejemplo completo: NADs de Multus en un solo YAML

```yaml
# manifest-templates/nads-cluster/template.yaml
id: nads-cluster
version: 1
description: NetworkAttachmentDefinitions del clúster
scope: cluster
params: {namespace: default, cni: macvlan}
outputs:
  - template: nads.yaml.j2
    mode: single
    path: nads.yaml
```

```jinja
{# nads.yaml.j2 #}
{% for nad in cluster.nads %}
---
apiVersion: k8s.cni.cncf.io/v1
kind: NetworkAttachmentDefinition
metadata:
  name: {{ nad.name }}
  namespace: {{ nad.namespace | default(params.namespace) }}
spec:
  config: '{{ {"cniVersion": "0.3.1", "type": params.cni, "master": nad.master | default("bond0." ~ nad.vlan), "ipam": {"type": "whereabouts", "range": nad.cidr}} | to_json }}'
{% endfor %}
```

Ejemplo per_item (un Netplan por nodo y uno combinado con una macro común):
ver `templates/manifests/netplan-node/` en ISoT. Ejemplo de salida no YAML:
`examples/demo-repo/manifest-templates/chrony-conf/`.

## 9. Reglas

- `IDX-001` aviso: índice commiteado ausente o desactualizado (ejecuta `isot index`).
- `REN-001` error: `renders.yaml` inválido, sitio/template/clúster
  desconocido o error de render (archivo:línea).
- `REN-002` aviso: salida con aspecto de secreto.
- `K8S-NAD-002` aviso: VLAN de una NAD no permitida en el trunk del leaf
  de los nodos del clúster.
